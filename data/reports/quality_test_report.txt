--- 1a. ICO Consistency ---
STATUS: FAIL

Unique ICOs tracked: 3,486
ICOs with multiple different names: 329
Of those, 227 are likely REAL BUGS (completely unrelated entities sharing
the same ICO), 43 are minor name variations (acceptable).

ROOT CAUSE: The parser is incorrectly assigning winner ICOs to buyers
(or vice versa). Pattern observed: in many cases, the same doc_id has
the buyer's name mapped to a winner's ICO. Examples:

  ICO 00151866 mapped to 7 different entities:
    "Ministerstvo vnutra SR" (real owner) AND "KVANT spol. s r.o.",
    "Zahoracke pekarne", "PYRA spol. s r.o.", etc.

  ICO 00165549 mapped to 6 different entities:
    "FN s poliklinikou F.D. Roosevelta BB" (real owner) AND
    "BAX PHARMA", "VIDRA a spol.", "Roche Slovensko", etc.

  Many cases appear in the SAME document (buyer and winner both assigned
  same ICO), suggesting the parser is picking up the wrong organization
  block for one of them.

This affects ~227 ICOs and is the most serious data quality issue.

--- 1h. Lot Data (pocet_casti vs actual casti array) ---
STATUS: FAIL

121 documents have mismatched lot counts.
ALL are off-by-one: the casti array has exactly 1 MORE element than
pocet_casti declares.

Pattern: The first element in the casti array has cislo=1 and an
empty nazov (it appears to be a "header" lot or a summary lot that
shouldn't be counted). The real lots start from the second element.

Example: doc 1399732 declares pocet_casti=5, but casti array has 6:
  lot 1: (empty name -- likely summary/header)
  lot 2: "Lieky ATC skupiny S01LA05..."
  lot 3-6: (real lots)

This is a TED parser bug where the summary lot is included in the array.
